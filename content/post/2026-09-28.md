# Nix is messy but also beautiful

When I first moved to Linux, I started with Ubuntu.

There were tons of tutorials, videos, and guides recommending it, so it was probably the easiest choice for someone who was just getting started. At first, everything worked pretty well. I could customize the desktop, change the tools I used, and configure almost everything around my own workflow.

But the more I used Ubuntu, the more I started to notice problems with its package management.

## The problem with my workflow

The first problem was the amount of **leftover packages**.

Some packages are surprisingly difficult to completely remove because they may have been installed from different sources. Even when a tool tells you that it can remove a package, what was installed may not simply be the application itself. It can also include libraries, dependencies, or packages required by some piece of hardware.

Because of that, cleaning up the system could become surprisingly annoying.

The second problem was **reusability**.

Usually, if you want to keep your workflow across different machines, you store your dotfiles and push them to GitHub. Then, when you move to another computer, you can clone the repository and restore your configuration.

Sounds simple enough.

Except the dotfiles are not really enough.

They depend on the packages installed on the machine.

When moving to a new computer, I still had to remember which packages were required for my configuration to work. I also had to install them, configure them, and sometimes spend quite a lot of time fixing things that worked perfectly fine on the old machine.

Then there was another problem: **updates**.

A package might receive a new version with a different API or behavior, and suddenly an old configuration no longer works the way it used to.

At that point, my dotfiles were reusable only as long as the environment around them was also compatible.

And this was the part that started bothering me.

## Dependency hell

One of the things that annoyed me the most on Ubuntu was installing Ruby gems.

At one point, I was trying to get some versions of Rails working. Some of them could not properly use the Ruby libraries installed through `apt`, while another setup seemed to work with packages installed through Snap.

I kept installing and reinstalling things.

Different Ruby versions were involved. Different package sources were involved. And somehow, after all that, it still did not work the way I wanted.

This was basically **dependency hell**.

It was not necessarily that Ubuntu was incapable of running the software. The problem was that I had too many pieces of the environment that had to agree with each other.

That experience was one of the reasons I started looking for another operating system.

And that was when I found NixOS.

## Meeting NixOS

NixOS immediately caught my attention because of one simple idea:

**The operating system itself can be configured as code.**

As described on the NixOS website, the system configuration can be declared and reused instead of being manually recreated every time.

Underneath NixOS is **Nix**, a functional programming language and package management system. The way Nix approaches packages, dependencies, and environments is quite different from what I was used to with traditional Linux distributions.

There is a lot more to how Nix actually works, but I will leave that for another article because explaining Nix properly is basically opening another rabbit hole.

And NixOS itself is already enough of a rabbit hole.

## Nix is a rabbit hole

Nix has a lot of features.

It is also extremely complicated.

One thing I noticed after spending more time in the Nix ecosystem is that the community tends to have many different ways of solving the same problem.

Sometimes this is great.

Sometimes it is confusing as hell.

There are many tools, many configurations, many opinions, and many different approaches to building a Nix system. Everyone seems to have their own idea of what the "correct" way to do something is.

But I cannot really complain about that.

Some of these projects are genuinely impressive.

Nix can be used for things ranging from managing a desktop environment to configuring servers, routers, development environments, and CI/CD pipelines.

The ecosystem is much larger than I initially expected.

And among all those things, two of them immediately caught my attention:

**flakes** and **Home Manager**.

## Flakes and Home Manager

Flakes are still somewhat controversial in the Nix community, partly because they try to solve a lot of problems at once.

For me, the interesting part is that a flake can describe an environment in a way that makes it much easier to reproduce and share.

I can define my system configuration as code, put it in Git, and then use the same configuration on another machine.

Home Manager is mainly focused on managing the user's environment and configuration files, cause one of its most useful features is how easy it is to manage dotfiles and create symlinks to them.

This makes configuration much easier to move around.

I do not have to manually copy every configuration file to a new machine. I can keep the configuration in one place and let Nix take care of putting it where it belongs.

It is a small thing, but once you start managing a lot of configuration, it becomes really useful.

## Why I still use NixOS

NixOS is a rabbit hole in the most literal sense.

The deeper you go, the more things you discover.

Then you realize that the thing you were trying to configure five minutes ago requires learning three other concepts first.

And somehow, you keep going.

But once you start getting comfortable with it, NixOS becomes a very powerful tool, especially for programmers.

The biggest thing for me is not that NixOS magically makes configuration simple.

It does not.

In fact, sometimes it makes things more complicated than they need to be.

What it gives me is **reproducibility**.

My operating system, development environment, packages, and configuration can be described as code. That code can be versioned, shared, reused, and applied to another machine.

That changes the way I think about my computer.

Instead of treating the operating system as something I install once and slowly modify until it becomes a mess, I can treat it more like another project.

And maybe that is why I still like NixOS.

It is messy.

It is complicated.

Sometimes it feels like everyone in the ecosystem is solving the same problem in a completely different way.

But once everything finally works, there is something strangely satisfying about knowing that most of it can be reproduced from a bunch of configuration files.

NixOS is messy, but it is also beautiful.

And so far, I do not regret falling into the rabbit hole.
